# x402 payments on Hedera

An API asks to be paid inside the request: it answers `402 Payment Required` with a price, the
client pays and sends the request again, and the API answers. Web2 analogy: Stripe built into
HTTP, with no checkout page, account or API key.

We use the official x402 packages (`@x402/core`, `@x402/hono`, `@x402/fetch`, `@x402/hedera`,
2.30.0) and the spec's **`transferExecutor`** method for Hedera: the money moves through a
contract, here our spending-limit contract (MandateRegistry), so the user's limit, the undo
window and pay on delivery all hold on every x402 payment. The official packages don't implement
`transferExecutor` yet, so we run our own facilitator for it (`packages/x402`).

## Flow

```
AI agent ──GET /quote──────────────────────────▶ merchant API (official x402 paywall)
         ◀── 402: 0.001 USDC to 0.0.hotel, transferExecutor, executors [registry]
signs a payment its limit allows (EIP-712)
         ──GET /quote + PAYMENT-SIGNATURE ─────▶ merchant ──/settle──▶ our facilitator
                                                                       │ simulate the exact call
                                                                       │ submit it (relayer pays)
                                                                       │ check the ledger record
                                                                       ▼
                                                      MandateRegistry.executeTransfer(...)
         ◀── 200 + answer + PAYMENT-RESPONSE (Hedera tx id) ──
```

Two kinds of price, both plain `transferExecutor` payments:

| `payTo` | What happens | Example |
|---|---|---|
| the merchant | paid now | 0.001 USDC per quote |
| the registry, with `extra.escrow` (payee, undo window, delivery deadline, review) | held: undo window, then paid on delivery; Hedera pays it out after the review | 0.02 USDC to book a room |

## Who controls what

| Who | Can | Can't |
|---|---|---|
| AI agent | Sign payments its limit allows | Pay outside its limit or allowed merchants; reuse a payment; shorten the undo window (it's in what it signs) |
| Merchant | Set prices and terms in its 402 | Be paid more than quoted, or by any other route than the registry |
| Our facilitator (relayer key) | Pay the fee and submit the call | Move money itself: it only wraps the call in a `ContractExecuteTransaction`; it never takes calldata from the client and only calls admitted contracts |
| Log writer | Write `x402.settled` to the public log | Anything else |

## What our facilitator checks (spec `transferExecutor`)

- **Before:** network, method and payload shape; the contract is admitted (default deny); the
  asset is an HTS token with no custom fees; payer and payee resolve to EVM addresses (alias
  first); the exact `executeTransfer` call, built from the requirements, simulates cleanly with
  the gas it will submit with (400k).
- **After:** a `SUCCESS` receipt isn't enough. Across the transaction and its child records,
  `payTo` gained exactly the amount, the payer lost exactly that, no other account or token
  moved, and only the fee payer lost HBAR. A payment already in flight can't be submitted twice.

| Path | What |
|---|---|
| `packages/x402/src/client-scheme.ts` | The AI's side: signs direct or held payments; refuses short undo windows |
| `packages/x402/src/server-scheme.ts` | The merchant's side: prices, admitted contracts, settled before the route runs |

## Gotchas found

- The paywall settles *before* the route runs ("upfront"), so a refusal's reason comes back in the
  `PAYMENT-RESPONSE` header (`errorReason`), not in `PAYMENT-REQUIRED`.
- The official fetch wrapper's paid retry passes a `Request` from another copy of the fetch API:
  `instanceof Request` is false, so read `input.headers` by shape.
- Hosted facilitators (x402.org, Blocky402, Launa) only support `cryptoTransfer` today, which can't
  go through a contract, so spending limits need our own facilitator.
